# WEBWB — правила сопровождения проекта

Этот файл обязателен к прочтению при начале новой сессии разработки. Уточнения владельца проекта имеют приоритет.

## Основные правила

1. **Репозиторий `Lex26p/WEBWB` — источник истины.** Перед шагом читать актуальные файлы репозитория и `docs/STATE.md`. При необходимости сверять хеш коммита. Не опираться только на прошлый чат.
2. **Один шаг за цикл.** Работать по `docs/ROADMAP.md`; новый шаг начинать только после получения от владельца коммита или отчёта о предыдущем шаге.
3. **Код пишет и редактирует только ассистент.** Ассистент готовит конкретные готовые файлы и ZIP с относительными путями от корня репозитория. В архиве именно исходные файлы, а не скрипт, который их создаёт.
4. **GitHub изменяет только владелец.** Ассистент **никогда не делает** commit, push, PR или другие изменения в репозитории.
5. **Пути Windows:** рабочий каталог `C:\Projects\WEBWB`, загрузки `C:\Users\pereverworkki\Downloads`. В WSL: `/mnt/c/Projects/WEBWB`.
6. **Команды:** группировать по смыслу — отдельно PowerShell (распаковка), WSL (сборка/проверки) и Git (commit/push). Простые команды без лишних действий. В блоке Git использовать `git add .`, не выдавать `git diff --check`.
7. **Документация:** в каждом шаге обновлять `docs/STATE.md`; если изменились решения или план — соответствующие документы. В `STATE.md` фиксировать, что *подготовлено*, что *проверено*, и что *подтверждено коммитом* (не путать эти состояния).
8. **Проверки:** по возможности добавлять в архив небольшой тестовый скрипт (`tests/`), запускаемый **одной командой** в WSL. Скрипт проверяет текущий этап автоматически, не перезаписывает пользовательские данные и выводит понятный результат. Ручные проверки давать только там, где без них нельзя. Не утверждать, что тест выполнен, если он фактически не запускался.

## Технологические ограничения

- Frontend: HTML, CSS, Vanilla JavaScript без React и сборщика.
- Backend: C++, предполагаемый стандарт C++17, CMake; собирать и тестировать в WSL с имеющимся toolchain. На шаге 04 уточнить HTTP/JSON зависимости и способ сборки под WB.
- Данные: JSON и файлы на контроллере, без СУБД на начальном этапе.
- MQTT: браузер в режиме просмотра через WebSocket; редактор не отправляет команды. Backend не обрабатывает MQTT и не исполняет автоматику.
- Авторизацию приложения по решению владельца не разрабатывать. Рассчитывать на локальную сеть, не публиковать сервис в Интернет; при этом проверять входные данные, безопасно работать с файловыми путями и ограничивать размер запросов.
- Не расширять редактор новыми функциями без согласования. В частности, добавление из палитры должно быть **только перетаскиванием**, без обработки клика (шаг 02).

## Формат ответа по каждому шагу

1. Короткая цель и что изменено.
2. Перечень прочитанных релевантных файлов и основание (коммит).
3. Ссылка на ZIP с готовыми файлами (структура путей совпадает с репозиторием).
4. Команда распаковки в `C:\Projects\WEBWB` из папки Downloads.
5. Команды сборки/проверки в WSL (если нужны); что проверить вручную.
6. Отдельный блок Git-команд, включая `git status`, `git add`, `git commit`, `git push`, получение `git rev-parse HEAD`.
7. Ожидать хеш коммита или ошибки владельца; не начинать следующий шаг в этом же цикле.

Никогда не включать `.git/`, бинарники и временные `build/` в ZIP с исходниками. При распаковке в существующий репозиторий не удалять пользовательские файлы.

## Тестирование и запуск начиная с шага 07

- В каждой итерации включать проверочные скрипты и давать простые команды; `bash tests/check.sh` — основной автоматический тестовый цикл (WSL).
- Для ручной проверки редактора через C++ API запускать `bash tests/run_editor.sh` и открывать `http://localhost:8090/` в браузере Windows. Не требовать ручного набора серии curl-запросов.
- `tests/dev_server.py` существует только для разработки на WSL; в production nginx заменяет локальный сервер. Не подменять им C++ backend.
- Оставаться в одном шаге до подтверждения SHA владельцем.
