## Пример

```json
{
  "version": 3,
  "title": "Моя панель",
  "root": {
    "id": "page",
    "type": "container",
    "name": "Страница",
    "style": { "width": "100%", "backgroundColor": "#ffffff" },
    "children": [
      {
        "id": "el_light",
        "type": "button",
        "name": "Кнопка света",
        "style": { "borderRadius": "12px" },
        "text": "Свет"
      }
    ]
  }
}
```

Полный пример, сгенерированный существующей моделью редактора: `tests/fixtures/project-v3.json`.

## Ограничения текущего валидатора

- Размер исходного документа — до **1 МиБ** (1 048 576 байт).
- Корень JSON — объект с `version: 3`, строкой `title` (до 120 символов) и объектом `root`.
- `root.type` строго равен `container`.
- Поддерживаемые типы узлов: `container`, `text`, `button`, `switch`, `slider`.
- Каждый узел содержит `id`, `type`, `name` и `style`.
- `id` — уникальная внутри проекта строка из 1–80 символов `[A-Za-z0-9_-]`.
- `name` — строка до 150 символов; `style` — объект со свойствами из списка `STYLE_KEYS` модели JS. Значения стилей — строки до 120 символов.
- Контейнер обязательно содержит массив `children`; у других типов его быть не должно.
- Текст, кнопка и ползунок содержат строковое поле `text` (до 10 000 символов).
- Переключатель содержит `checked` типа `boolean`.
- Ползунок содержит числовые `min`, `max`, `step`, `value`: `min` в диапазоне -10000…10000, `max` не менее `min + 1` и не более 10001, `step` в диапазоне 1…10000, `value` в пределах `[min, max]`.
- Не более **400 элементов**, корневой элемент считается первым. Вложенность до **20 уровней ниже корня**.

При проверке используются JSON-типы, а не преобразование всех значений в строки. Лишние поля объекта не интерпретируются валидатором, но неизвестные свойства внутри `style` отклоняются. При расширении модели (например, MQTT-поля) пересмотреть контракт и тесты, а при несовместимых изменениях повысить версию формата.

### Совместимость

`frontend/js/model.js` уже умеет импортировать старые проекты v1/v2 и приводить их к формату 3. Backend **не мигрирует** старые форматы: открыть такой проект в редакторе и заново экспортировать JSON версии 3.

Схема не превращает JSON в HTML и не выполняет переданные стили. Начиная с шага 06 backend **проверяет JSON перед записью** на диск.

## Проверочный API (шаг 05)

```text
POST /api/projects/validate
Content-Type: application/json
<тело — проект JSON>
```

- `200 {"valid":true,"version":3}` — проект соответствует формату.
- `400 {"valid":false,"error":"invalid_project","detail":"..."}` — JSON некорректен или схема нарушена.
- `405` — другой HTTP-метод.

Этот маршрут нужен для проверки при разработке; это **не** создание проекта и не постоянное хранилище.

## Сохранение (шаг 06)

JSON версии 3 сохраняется в `<data-dir>/projects/<id>.json`; операции CRUD описаны в [API.md](API.md). ID генерируется сервером, не зависит от имени файла, заголовка или ID корневого контейнера. Файлы проверяются при чтении, а обновление выполняется через временный файл и переименование. Редактор подключится к серверному API отдельно на шаге 07.
