# WEBWB — архитектура

Дата первичного согласования: 19.10.2026. Состояние: **шаги 01–10 подтверждены; шаг 11 — получение MQTT-состояний, подготовлено к проверке**. C++ backend хранит проекты, шаблоны, изображения и настройки; MQTT реализуется исключительно в viewer.

## Назначение

Визуальный конструктор лёгких интерфейсов управления для Wiren Board. Это **не SCADA** и не конструктор обычных сайтов. Доступные пользователю элементы ограничиваются простыми HTML-контейнерами и базовыми компонентами. Нельзя привязывать тип компонента к модели физического устройства: каждый компонент работает с произвольно заданными MQTT-топиками.

## Составные части

1. **Редактор (`frontend`)** — браузерное приложение на HTML/CSS/Vanilla JS. Создаёт дерево элементов, редактирует CSS-свойства, в будущем задаёт MQTT-привязки. Никаких MQTT-команд при редактировании.
2. **Просмотр (`viewer`, шаг 10)** — отображает сохранённую страницу и, после реализации MQTT-этапов, подключается к MQTT WebSocket для чтения состояния и отправки команд. Реализует отображение, но **не логику автоматизации**.
3. **C++ backend (шаги 04–06)** — небольшой HTTP API для проектов, шаблонов, загруженных изображений и общих настроек. Не соединяется с MQTT, не управляет устройствами.
4. **Файловое хранилище** — JSON проектов/шаблонов/настроек и изображения; без базы данных. Планируемое расположение на WB: `/mnt/data/webwb/` (требует проверки на устройстве).

```text
Браузер (редактор) ---> HTTP API ---> C++ backend ---> JSON / файлы
Браузер (просмотр) -> HTTP API ---> C++ backend ---> проект JSON
Браузер (просмотр) <-> MQTT over WebSocket <-> Mosquitto / wb-rules
```

В промышленном развёртывании статические файлы планируется отдавать через существующий веб-сервер контроллера (вероятно, nginx), API backend проксировать через него на локальный HTTP-порт. Эти детали **не реализованы и не проверены** на шаге 01. Если план будет изменён, зафиксировать здесь.

## Модель страницы

- Дерево элементов. Корневой контейнер содержит вложенные контейнеры и компоненты.
- Типы на первой итерации: контейнер, текст, кнопка, переключатель без обязательной подписи, ползунок.
- Базовые общие свойства: название, размеры, отступы, фон, граница со скруглением, положение при свободном размещении.
- Контейнер организует вложенные элементы с помощью обычных CSS-свойств `display: flex`, `flex-direction`, выравнивания по X/Y; при свободном размещении используется CSS `position`.
- Перемещение и добавление из палитры — перетаскиванием. Клик на палитре не должен добавлять элемент (задача шага 02).
- Сохранение компонента или контейнера со всем поддеревом как шаблона; копирование и перемещение по дереву.
- Формат проекта — JSON-дерево, не сырой HTML-код. За совместимость с данными из v0.3 отвечает будущий шаг 05. Текущий прототип уже умеет экспортировать свой JSON.

## Планируемый API

Реализованы маршруты проектов и шаблонов (см. [API.md](API.md)). Загрузка изображений и общие настройки пока не реализованы.

- CRUD проектов;
- Получение/сохранение шаблонов;
- Загрузка и выдача изображений;
- Чтение и изменение настроек приложения.

## Хранение, запуск и безопасность

- Данные проектов сохраняются на контроллере; `localStorage` прототипа — только временное решение.
- Файлы должны записываться с безопасной заменой (временный файл + переименование); нужна проверка размеров/форматов/путей и версионирование JSON.
- C++ backend предлагается привязать к loopback-интерфейсу, а внешний доступ организовать через существующий веб-сервер WB после проверки окружения.
- **Собственную авторизацию не реализуем**, по решению владельца. Это подходит только для контролируемой локальной сети. Отсутствие авторизации не означает отсутствие валидации данных и запросов.
- Сборка C++ в WSL, CMake; конкретный компилятор WB и архитектура процессора ещё не определены. Не выбирать библиотеки и ABI до проверки toolchain.

## Что не делаем на начальном этапе

Нет React, npm/build frontend, SQL, собственного MQTT-брокера, backend MQTT-клиента, исполнения правил, автоматического распознавания всех устройств, облака, сложных CSS-конструкторов, пользовательских ролей и собственной авторизации.

## Текущая реализация — шаг 03

Редактор остаётся автономным и запускается через `frontend/index.html`, включая `file://` без локального HTTP-сервера.

- `frontend/js/model.js` — модель JSON, значения по умолчанию, нормализация импортов, общие утилиты.
- `frontend/js/view.js` — отображение дерева, холста и шаблонов; зависит от модели и переданного состояния.
- `frontend/js/properties.js` — поля свойств (включая подсказки), изменение CSS; зависит от модели и переданного состояния.
- `frontend/app.js` — состояние текущего проекта, история отмены/повтора, шаблоны, копирование, Drag & Drop, обработчики событий и запуск приложения.
- `frontend/styles.css` — единый файл стилей без изменений в шаге 03.

`index.html` подключает скрипты обычными `<script defer>` в указанном порядке. Нативные ES-модули (`type="module"`) пока не применяем, поскольку из-за ограничений `file://` они потребовали бы локальный веб-сервер. Каждая часть заключена в IIFE; модель и фабрики UI передаются через небольшие глобальные точки интеграции `WBPanelModel`, `WBPanelCreateView`, `WBPanelCreateProperties`. Состояние проекта передаётся UI-модулям через объект с геттерами, чтобы операции «Новый», импорт JSON и Undo/Redo не оставляли устаревшие ссылки на предыдущий проект.

Формат сохранённого проекта (версия `3`) и ключи localStorage **не менялись**. Удаления функций или появления MQTT в шаге 03 нет. После внедрения backend механизм хранения будет заменён по последующим шагам.


## HTTP-сервер — шаг 04

- Backend — исполняемый файл `webwb_backend`, собирается CMake с C++17.
- HTTP реализован через **Boost.Beast + Asio** (заголовочные библиотеки; `Threads::Threads`, без собственного парсера протокола). На этапе проверки в WSL потребуются заголовки Boost (`libboost-dev`).
- Привязка: **127.0.0.1**, порт по умолчанию `8088`. Не слушает локальную сеть напрямую. Никакой собственной авторизации.
- Проверочный маршрут `GET /api/health` возвращает `200` и `{"status":"ok","service":"webwb"}`; остальные пути отвечают `404`, неподходящий метод у health — `405`.
- Опции запуска: `--port N`, `--data-dir PATH`, `--help`. По умолчанию каталог данных `/mnt/data/webwb`; на этом этапе он не создаётся и не используется.
- Ограничено чтение одного запроса: заголовки до 16 KiB, тело до 1 MiB, тайм-аут 5 секунд; соединения обрабатываются последовательно (достаточно для smoke-test, пересмотреть при разработке CRUD).
- Перед кросс-компиляцией требуется убедиться в наличии Boost для WSL toolchain, архитектуре и целевом ABI Wiren Board. Текущая успешная проверка на Linux **не доказывает** работоспособность на контроллере.
- Полный CRUD JSON, проверки путей и атомарное сохранение будут реализованы на следующих шагах.

## Формат JSON — шаг 05

- Контракт проекта v3 согласован с фактическим экспортом `frontend/js/model.js`; подробности в [`PROJECT_FORMAT.md`](PROJECT_FORMAT.md).
- Валидатор в `backend/src/project_validation.cpp` проверяет структуру, допустимые типы, ID, ограничение вложенности (20), узлов (400), размера (1 МиБ) и версию (3). Значения не нормализует и не сохраняет.
- Для разбора JSON выбран `json-c` (`libjson-c-dev`), системная библиотека C, используемая из C++17, в дополнение к Boost.Beast. Совместимость с WSL протестирована, под WB — ещё нет.
- Тестовый маршрут `POST /api/projects/validate` возвращает `200`/`400`. `GET /api/health` не изменён. Валидация станет общей точкой перед записью данных в следующем шаге.
- `--data-dir` пока только параметр, хранилище не создаётся. Формат v1/v2 принимает только frontend (он мигрирует в v3 при экспорте).

## Хранение проектов — шаг 06

- `webwb::ProjectStore` (`backend/include/webwb/project_store.hpp`, `backend/src/project_store.cpp`) принимает базовый каталог из `--data-dir`, создаёт подпапку `projects`.
- Разрешены только ID из 32 строчных шестнадцатеричных символов. Имя файла `<id>.json` не формируется из пользовательского названия; предотвращается `../` в пути.
- `POST /api/projects` сохраняет валидированный JSON v3 и выдаёт серверный ID; `GET /api/projects` возвращает ID и названия; отдельные `GET`, `PUT`, `DELETE` обслуживают `/<id>`.
- `PUT` пишет временный файл рядом с основным и атомарно заменяет его через `rename`. В Linux выполняется `fsync` файла. `GET` проверяет файл на корректность перед выдачей. Неизвестные и повреждённые файлы не исполняются.
- Директория данных выбирается оператором запуска, **не** HTTP-запросом. Сервер слушает только loopback.
- Синхронный HTTP-сервер и отсутствие совместного редактирования сохраняются; фронтенд подключим к API на шаге 07.
- Форматы успешных и ошибочных ответов описаны в `docs/API.md`.


## Серверные шаблоны — шаг 08

- `TemplateStore` (`backend/src/template_store.cpp`) хранит шаблоны в `<data-dir>/templates/`, по одному JSON на файл.
- Объект шаблона содержит `name` и дерево `node`; ID (32 hex-символа) задаёт сервер. Ограничение 30 штук.
- `validate_template` использует ту же валидацию типов узлов, вложенности (20), количества (400), стилей и допустимых значений, что и проект.
- API: `GET/POST /api/templates`, `DELETE /api/templates/<id>`; доступ из редактора через общий HTTP-origin.
- `frontend/app.js` использует серверную библиотеку; при первом успешном подключении существующие шаблоны из `localStorage` того же origin мигрируют в backend, при сбое локальный список не уничтожается. Шаблоны из `file://` могут быть недоступны новому HTTP-origin.
- В тестах используется Python dev-прокси; на Wiren Board для общего HTTP-origin позже настроим nginx. Сам backend MQTT не обрабатывает.


## Шаг 09 — файлы изображений и настройки

- `AssetStore` (`backend/src/asset_store.cpp`) хранит двоичные PNG/JPEG/WebP в `<data-dir>/uploads`. Не принимает SVG, не использует исходные имена файлов, отвечает на GET по случайному ID. Для фронтенда URL изображения — `/api/uploads/<id>`.
- `SettingsStore` (`backend/src/settings_store.cpp`) хранит общий JSON `{"title":"WEBWB"}` в `<data-dir>/settings.json`. Отдельный API GET/PUT. Состав настроек минимален и может расширяться по необходимости.
- В редактор добавлен компонент `image` и загрузка через свойства выбранного элемента. Проект остаётся JSON версии 3; `src` — URL изображения на том же сервере, а не вложенный бинарный файл.
- Dev-сервер Python только проксирует `/api/` и раздаёт frontend. Само хранение реализует C++ backend. При переносе на WB nginx заменит dev-сервер.
- Сами файлы изображений не включаются в экспорт JSON-проекта. Для переноса между контроллерами потребуется отдельная процедура резервного копирования `uploads/` вместе с JSON-проектами.


## Отдельный viewer — шаг 10 (ожидает подтверждения)

- Сохранённый проект доступен через `viewer.html?id=<32-символьный hex ID>` по **тому же origin**, что и frontend/backend API.
- `frontend/js/renderer.js` — единый рендерер дерева компонентов для холста редактора и отдельного viewer. Режимы отличаются настройкой интерактивности и подсветки выбранного элемента.
- `frontend/viewer.js` проверяет ID из параметра URL, делает `GET /api/projects/<id>` через `WBPanelAPI.load`, применяет нормализацию JSON и создаёт DOM без дерева, палитры и настроек. При ошибке показывает текстовое сообщение.
- `frontend/viewer.css` задаёт только внешний вид отдельной страницы; стили компонентов берутся из `frontend/styles.css`. На шаге 10 это демонстрационный просмотр **без MQTT**.
- В редакторе ссылка «Открыть панель» доступна после сохранения проекта. При несохранённых изменениях viewer показывает **последний сохранённый вариант**, не локальный черновик.
- `tests/dev_server.py` в WSL выдаёт новые статические файлы; в production это будет делать nginx.
- Изображение как самостоятельный компонент из шага 09 пока без изменений. В будущем вместо него пользователь предлагает фон обычного контейнера; реализация этой правки отложена до согласования.


## MQTT: получение статусов — шаг 11

- Редактор лишь записывает `mqtt.statusTopic` (и `mqtt.activeValue` для кнопки/переключателя) в узел JSON v3. При редактировании подключений к MQTT **нет**.
- В просмотре `frontend/js/mqtt_reader.js` открывает **один** MQTT 3.1.1 WebSocket, отправляет только `CONNECT`, `SUBSCRIBE`, `PINGREQ`, получает `CONNACK`/`PUBLISH`, при потере связи переподключается. MQTT `PUBLISH` **не отправляется**; управление отложено до шага 12.
- По умолчанию WebSocket URL — `ws(s)://<хост просмотра>/mqtt` (при размещении с nginx). Если необходимо, URL можно задать в ссылке просмотра параметром `mqttUrl`, например `ws://IP_WB:18883/`. На dev-сервере WSL `/mqtt` не проксируется, а реальный брокер не создаётся.
- Состояния используются для текста (дописать значение к подписи), кнопки (подсветка при совпадении), переключателя (отмечено при совпадении) и ползунка (числовое значение). С привязанного элемента нельзя отправить команду на шаге 11. Прочие компоненты остаются демонстрационными.
- Все MQTT-топики задаются вручную, без привязки к физическим моделям устройств. Поля необязательны; старые проекты открываются без изменений. Backend проверяет `mqtt`, но к брокеру не подключается.
- Проверка транспорта через `tests/mqtt_reader_test.js` использует имитацию WebSocket, без реального MQTT-брокера. Проверка на настоящем WB — на шаге 13–15.
